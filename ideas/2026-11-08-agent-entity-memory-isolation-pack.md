# Same-Week Agent Entity Memory Isolation Pack for Solo Operators

**Date:** November 8, 2026

## X signal (today)

X on 6–8 Nov 2026 is circulating Anthropic’s 6 Nov agent-memory research as a concrete failure mode for solo operators running more than one agent.

- @quantumspaceup (8 Nov): “@AnthropicAI tested agent memory on contract terms: one shared table kept 41 of 57 facts, because agents overwrote each other. one page per contract kept 57 of 57 (nov 6). same in marketing ops: give each agent its own record, not one shared sheet to fight over.”
- @MarMarLabs (7 Nov) and @AIC_Hugo (8 Nov) quote the same numbers and the two practical fixes: (1) one writer per page (split by entity), (2) version check on every save for pages that must be shared. “Last save wins” is silent data loss. Summaries also drop facts; the successful rebuild quoted terms word for word.
- Adjacent: Grok-bot “chief of staff” posts that give every agent its own memory file; notes that switching cost between personal agents is now high because memory does not transfer cleanly; and warnings that shared recall turns one bad note into every agent’s fact.

The catalog already covers shared-memory hygiene, harness floors (job + memory file + verification + stop rules), and completion receipts. It does not have a productized pack that inventories the buyer’s actual shared files, assigns single ownership or version checks per entity (client, contract, job, campaign), and ships the paste-ready isolation rules so multi-agent or repeated runs stop overwriting each other.

## Concept

Sell a **same-week agent entity memory isolation pack** when a solopreneur, indie hacker, or freelance operator is running (or about to run) multiple agents or repeated sessions that write to the same notes, tables, or memory files for clients, contracts, leads, or jobs—and currently risks silent overwrites.

The customer uploads (or pastes):

- list or export of current memory files, shared tables, Notion/Obsidian/Google Sheets, or agent note locations
- description of which agents or scheduled jobs write to them and on what entities (clients, contracts, campaigns)
- optional: sample of a conflict or “the note disappeared” incident

Agents plus one human operator return within 48–72 hours:

1. Shared-file inventory: every location two or more agents can write, tagged with current writers and entities.
2. Isolation map: recommended split—one page/file per entity with a single named owner, or version-check protocol for the few pages that must stay shared.
3. Per-entity page template: Markdown (or sheet) structure that stores word-for-word source quotes plus derived fields, with clear “do not summarize over source” rules.
4. Version-check / last-writer rules: paste-ready prompt or wrapper language that refuses a save if the version has advanced, or that routes writes to the owning agent.
5. Source ledger: every recommendation cites the provided materials or is marked operator assumption.
6. Migration starter: ordered steps to move the highest-risk shared file to the new pattern without losing existing notes.

This is **not** a full memory platform, **not** live instrumentation of agents, **not** a general hygiene audit, and **not** a transfer tool between completely different agent products. It is a productized desk that turns “agents keep overwriting the shared sheet” into an inspectable isolation pattern the solo can apply this week.

## Target user

- Primary buyer: solopreneurs, indie hackers, and freelance operators (EU/UK/US/Canada) already running two or more agents (or one agent across many client/job files) that share notes, CRM-like tables, or memory files.
- Urgent pain: a fact that was correct yesterday is missing or wrong today because another agent (or a later run) overwrote the shared table; or summaries have silently dropped source details.
- Existing workaround: keep everything in one chat window, manually copy-paste, or accept occasional silent loss.

## Why this works

## Execution plan (one person + agents)

**Agent 1 — Intake.** Accept file lists, exports, sample notes, and agent descriptions. Normalize, assign file ids, flag missing ownership info.

**Agent 2 — Inventory & map drafter.** Extract shared locations, current writers, and entities; propose one-writer splits or version checks. Tag with citations.

**Agent 3 — Template & rule writer.** Draft the per-entity page template (word-for-word sources) and the paste-ready version-check or ownership prompt language.

**Agent 4 — Migration writer.** Produce the ordered starter steps for the highest-risk file.

**Human operator.** Remove vague items, tighten ownership to real decision cost, confirm every claim is checkable against the materials, and export Markdown + PDF. Do not instrument the live agents or migrate the files yourself.

Stack to start: existing coding/browser agents, one LLM, plain Markdown, Stripe Payment Link, mailbox. No product UI until the fifth paid job.

## Risks and mitigations

- Invented ownership or rules: every item cites provided materials or is marked “not specified — operator assumption.” Operator rejects drafts that invent run behavior.
- Confidential client notes: isolated processing, no training on client materials, delete after 30 days unless they opt in.
- Overlap with shared-memory hygiene or harness packs: this pack is specifically the isolation pattern (one writer per entity page + version checks + word-for-word sources) for files that multiple agents already share. Hygiene and single-job harnesses stay separate. Implementation stays with the buyer.
- Buyer expects a live migration or full memory platform: deliver the pack for the materials provided and stop. Moving the files or building a new store is a separate engagement.
- Thin materials: if the customer has only “agents share a Notion” and no file list or conflict example, return a short gap list and partial refund rather than invent an isolation map.
